# ecosystem/exclude.txt
#
# Distributions the ecosystem tools must never pick automatically.
#
# `ecosystem-tickets.py --queue` never offers a listed distribution in the
# ecosystem-dist-queue skill's work order. `ecosystem-sweep.py` skips them in a bulk `--all` /
# `--prefix` / `--status` / `--stale` selection; `--only <name>` still measures
# one explicitly, so a deliberate re-check after a policy changes is not
# blocked by this file.
#
# An entry belongs here only when the distribution was investigated and found
# permanently unfixable without a decision the project has already made and
# does not intend to revisit -- a decision AGENTS.md reserves for the user, or
# a superseding ADR -- never because it "looks hard". This is NOT the same as
# `no_baseline` (rakudo fails it too, so it is already excluded from the KPI on
# its own): every entry here is a distribution rakudo passes and mutsu,
# correctly, cannot -- see each reason below and the ADR/issue it cites.
#
# A second kind of entry pins one release: a distribution whose own suite rakudo
# passes only by accident of rakudo's implementation state (a test-side
# assumption, not a mutsu gap), excluded until a new release may have fixed it.
# The pin stops applying as soon as the index shows another version, so the
# next release is measured again with no one having to delete the line.
#
# Format: <Dist::Name> <one-line reason, ideally citing an issue and/or ADR>
#     or: <Dist::Name>@<version> <one-line reason>   (that release only)
# Blank lines and lines whose first non-blank character is `#` are ignored.
# Keep sorted by name.

App::MoarVM::Debug -- the MoarVM:: namespace is out of scope (user decision 2026-10-31, #15808): it is a client of MoarVM's remote debug protocol; mutsu is not a MoarVM.
App::MoarVM::HeapAnalyzer::Model #15808 -- the MoarVM:: namespace is out of scope (user decision 2026-10-31): it analyses MoarVM heap snapshots (and relies on rakudo's hidden deprecated core `from-json`, which mutsu will not add); mutsu is not a MoarVM.
Gauge #15266 -- its first statement dies on `$*VM.version < v2022.04`, the MoarVM release coordinate; mutsu is not a MoarVM and will not report one, and the module is not handled until it supports mutsu (user decision 2026-10-29). `--only Gauge` still measures it for a re-check once the module changes.
LibraryMake #12829 -- get-vars dispatches on $*VM.name (moar/jvm) and dies on anything else; mutsu reports 'mutsu' and will not report 'moar' (same principle as ADR-0104; user decision 2026-09-25, see uniprop).
MCP::Server@0.7.2 #14684 -- its t/21-elicitation-dispatch subtest "A round that answers only some of the questions" depends on rakudo's thread-pool state, not on a language guarantee: it passes 10/10 on a cold rakudo (one worker, FIFO) and 7/10 on rakudo once the pool is warm, the same subtest failing (ADR-15967 §2.1/§3). The current release is not a test target (user decision 2026-11-09); a new release is measured again.
MoarVM::Bytecode #13511 -- its suite parses CORE.c.setting.moarvm found under $*EXECUTABLE.parent(3) (the running compiler's install tree); mutsu is not a MoarVM and ships no .moarvm files, so it can only pass by pointing at a rakudo install.
MoarVM::Profile -- the MoarVM:: namespace is out of scope (user decision 2026-10-23): it reads MoarVM's own profiler output; mutsu is not a MoarVM.
MoarVM::Remote -- the MoarVM:: namespace is out of scope (user decision 2026-10-23): it drives MoarVM's remote debug protocol (its suite spawns `nqp`/moar); mutsu is not a MoarVM.
Rakudo-Type-Introspection #15616 -- not supported (user decision 2026-11-08, superseding the 2026-11-03 decision to implement it): it exists to read rakudo's own undocumented internals (the version-gated `CORE::v6c|v6d|v6e` namespaces, `CORE::v6c::PseudoStash`, `.^is-implementation-detail`), which raku-doc does not specify; the distribution is not handled.
Rakudo::Options #16953 -- not supported (user decision 2026-11-08): it is a rakudo-specific distribution, and its `t/02-with` asserts that MoarVM's specializer log (`MVM_SPESH_LOG`) writes a file starting with 'Received Logs'; mutsu is not a MoarVM and will not fake the artefact (ADR-0130 would otherwise apply to that one file). The other four test files match rakudo.
Rakudo::Version #8945 -- its own BEGIN checks $*RAKU.compiler.name eq 'rakudo'; ADR-0104 already rejected outright ever spoofing .name, so this can only pass by superseding that decision.
Template::HAML #16451 -- not supported (user decision 2026-11-08, ADR-16451): its precompilation test asserts rakudo's `<root>/.precomp` storage layout, which mutsu will not copy (its precompilation store is a per-user content-keyed cache, ADR-11756); the distribution is not handled.
uniprop -- dispatches on $*VM.name (moar/jvm/js) and dies on anything else; mutsu reports 'mutsu' and, by the same principle as ADR-0104 (never claim to be another implementation), will not report 'moar' (user decision 2026-09-25). Its moar branch also needs nqp::getuniprop_* / nqp::unipropcode.
