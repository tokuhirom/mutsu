# Flaky test quarantine ledger.
#
# Format:  <test-path>  <added:YYYY-MM-DD>  <review:YYYY-MM-DD>  <reason>
#
# A listed test is re-run (up to 3 attempts) by scripts/flaky-retry.sh, which
# both test runners go through, so a single unlucky roll no longer blocks a
# merge. It is NOT immunity: a deterministic failure fails all three attempts
# and still blocks. Every retry is reported in the CI job summary.
#
# The bar for adding an entry is deliberately high -- the non-determinism must
# be understood and must not be a defect in mutsu. Crashes, wrong answers, and
# anything whose root cause is unknown are never quarantined; they are bugs to
# fix. Read docs/flaky-test-policy.md before touching this file, and back every
# entry with numbers from scripts/ci-flake-survey.sh and scripts/flake-repro.sh.
#
# Entries expire: `make check-flaky-list` fails once the review date passes,
# which forces a re-measurement rather than a silent permanent quarantine.
#
# Keep sorted by path.

battery:Crypt::Random/03-uniform.t 2026-10-02 2027-01-02 Statistically flaky by design (#10885). The upstream test draws three values with crypt_random_uniform(10000) and asserts `$one != $two && $two != $thr`, which a uniform RNG violates with probability ~2/10000 per run; the battery gate runs it on every CI run, so an occasional red is expected (seen once: PR #10871, run 36987942696, `FAIL(ok=1/2,notok=1)`, passed on rerun). Not a mutsu defect, measured 2026-10-02: 20000 draws in one process gave 3 neighbour collisions (expected ~2), 8657 distinct values (expected ~8647) and none out of range; a 64000-byte histogram of crypt_random_buf spanned 211..289 per value (expected ~250); 3400 runs of the file 8-way parallel on 4 cores all passed. The bad-read theories do not fit either: Crypt::Random::Nix dies on a short /dev/urandom read rather than returning a value. The gate now prints the failing `not ok` lines, so a recurrence that is test 2 (out of range) would be a real bug, not this entry.
