# Concurrent HTTP sessions increment one shared SessionData instance's counter instead of their own

## Affected tests
- `t/http-session-inmemory.rakutest` subtests 8, 9 ("No session confusion with concurrent clients (A)/(B)")
- `t/http-session-persistent.rakutest` subtests 8, 9 (same names, same shape)

## Repro
Found while verifying the fix for `sibling-thread-my-array-merges-through-root-atomic-lane` (PR
landed 2026-08-10). That fix made `__mutsu_atomic_arr::`/`__mutsu_atomic_hash::` lanes resolve at
the lineage owning the base name instead of unconditionally at root, which stopped two concurrent
`start` blocks' distinct `my @a` bindings from merging into one array — **and it genuinely fixed
that part of this test**: both `@a`/`@replacer`-style arrays are now the correct length (5
elements each, in client-consistent order) instead of one 9-10 element merged array.

But the test still fails, with a different symptom now:

```
not ok 8 - No session confusion with concurrent clients (A)
# expected: 'Visit 1,Visit 2,Visit 3,Visit 4,Visit 5'
#      got: 'Visit 1,Visit 3,Visit 5,Visit 7,Visit 9'
not ok 9 - No session confusion with concurrent clients (B)
# expected: 'Visit 1,Visit 2,Visit 3,Visit 4,Visit 5'
#      got: 'Visit 1,Visit 2,Visit 4,Visit 6,Visit 8'
```

Odd numbers go to client A, even (mostly) to client B, 1..9 total across both — i.e. ONE counter
is being shared and incremented by both clients' concurrent requests, even though each client has
its own cookie-jar and (per the now-fixed array evidence) its own request array.

The route handler (`t/http-session-inmemory.rakutest`):
```raku
my class SessionData does Cro::HTTP::Auth {
    has $.count is rw = 0;
}
my $app = route {
    get -> SessionData $session, 'hits' {
        content 'text/plain', 'Visit ' ~ ++$session.count;
    }
}
```
`Cro::HTTP::Session::InMemory[SessionData]` (`lib/Cro/HTTP/Session/InMemory.rakumod`) stores each
session's `SessionData` instance in a `my monitor SessionStore`'s private `%!session-lookup` hash,
keyed by a per-client cookie value generated by `generate-session-id()`. Two different clients
should get two different cookie values, two different hash entries, and therefore two distinct
`SessionData` instances whose `$.count` attributes are independent.

## What's ruled out
A minimal isolated repro (`tmp/repro-monitor-session-count.raku`) modeling the exact same shape —
a `my monitor Store` with a private `%!lookup` hash mapping a key to a lazily-created object, two
concurrent `start` blocks calling `$store.get-or-create($key)` with DIFFERENT keys and
`++$s.count`-ing the returned object 5 times each with a small sleep between calls — does **NOT**
reproduce the bug: both threads correctly get `1,2,3,4,5` independently, run repeatedly. So the
monitor/hash-of-objects mechanism itself is sound under concurrency; the bug needs something more
specific to the real pipeline: the HTTP router's per-request typed-parameter injection
(`get -> SessionData $session, ...`, which binds `.request.auth` to the route parameter — the
binding site was not located in this pass, `Cro::HTTP::Router.rakumod` under this dist's `lib/`
doesn't obviously contain it), the `Cro::HTTP::Session::InMemory` `process-requests`/
`process-responses` `supply whenever` middleware pipeline, or the request/response object's
identity as it flows through concurrent client connections.

## Fix direction (not investigated yet)
Needs a repro closer to the real shape than the isolated monitor test above — likely instrument
(or shadow-bisect) `Cro::HTTP::Session::InMemory.rakumod`'s `!existing-session`/`start-session`
and the router's typed-auth-parameter binding to see whether two concurrent requests are
resolving to the same `SessionData` instance (session store bug: same cookie value handed to both
clients, or hash lookup collision) or to two different instances whose `$.count` attribute cells
are nonetheless aliased (attribute-cell-sharing bug, the family documented in
`hashdata-layout-unsafe-cast-audit`/session memory notes about `$_`/`self` leaking across frames).
Print/log the session cookie value and `self.WHICH`/`$session.WHICH` on each request to
distinguish the two hypotheses before touching any code.

## Verification
- `t/http-session-inmemory.rakutest` subtests 8-9: 5 elements each, `Visit 1,2,3,4,5` for both A
  and B (not interleaved).
- `t/http-session-persistent.rakutest` subtests 8-9 likewise.
- `tmp/repro-monitor-session-count.raku` stays green (it already is — keep it as a negative
  control pin once a real repro is found, so the two mechanisms don't get reconflated again).
