# `Foo.counter++` on a class-level attribute accessor now works from OUTSIDE a method body too

`my $.counter` / `our $.counter` in a class body declares a class-scoped
lexical plus a public accessor method (`news/2026-08/class-scoped-my-dot-attribute-persists.md`).
Plain assignment to that accessor from outside a method body already worked
(`Foo.counter = 99`), and `$.counter++` *inside* a method body already worked
(via the cell-direct `read_self_attr_cell`/`write_self_attr_cell` machinery).
But the increment/decrement forms of the accessor *call itself*, from outside
any method, were still unsupported:

```raku
class Foo {
    my $.counter = 0;
}
Foo.counter++;
say Foo.counter;
```

- `raku`: `1`
- mutsu (before this fix): `Cannot resolve caller postfix:<++>(...); the
  parameter requires mutable arguments`

## What rakudo actually does

`Foo.counter` is generated by `my $.counter` / `our $.counter`, and it is
**not** `is rw` — `.^lookup('counter').rw` is `False` in both raku and mutsu.
Yet `Foo.counter++` still works in raku. The reason is that Raku's `++`/`--`
are not special-cased on the accessor's own `rw`-ness at all: a method-call
expression used as an lvalue goes through the same "call the accessor, get
back a container, read-modify-write through that container" machinery that
already backs `Foo.counter = 99` and `Foo.counter += 5` — both of which
*already worked* in mutsu before this fix, because mutsu's compound-assignment
compilation (`compound_expr.rs`) already re-evaluates the original target
expression (`Expr::BareWord("Foo")`, not just `Expr::Var`) to reach the
class-level-attribute arm of `assign_method_lvalue_with_values`
(`src/runtime/methods_mut_method_lvalue.rs`). `Foo.counter++` was missing only
because the postfix/prefix `++`/`--` *compiler* arms for a method-call target
(`src/compiler/expr_postfix.rs`) matched `Expr::Var`/`Expr::ArrayVar`/
`Expr::HashVar` targets only — never `Expr::BareWord` — so a bareword-target
method call (the type object, `Foo`) fell through to the generic
`__mutsu_incdec_nomatch` path and raised the "requires mutable arguments"
error unconditionally, regardless of whether the callee was a class-level
attribute accessor or not.

## The empirical surface (verified against `raku`)

| Form | outside a method, type object | outside a method, instance | ordinary non-rw `has $.x` (instance) |
|---|---|---|---|
| `.counter++` | `1` | `1` | **throws** (`X::Multi::NoMatch` in raku) |
| `.counter--` | `-1` | (not separately tested; symmetric) | throws |
| `++.counter` (prefix) | `1` | (symmetric) | throws |
| `.counter += 5` | `5` (already worked pre-fix) | n/a | throws (`X::Assignment::RO`) |
| `.counter x= 2` | `"aa"` (already worked pre-fix) | n/a | n/a |
| `.counter = 99` (control) | `99` (already worked pre-fix) | n/a | throws (`X::Assignment::RO`, "Cannot modify an immutable Int") |
| `has $.x is rw`, `.x++` | n/a | `1` (already worked) | n/a |

Both `my $.counter` and `our $.counter` behave identically on this matrix. The
`@.`/`%.` sigil variants surfaced a separate, pre-existing bug (`Foo.list.push(1)`
and `Foo.hash<a> = 1` from outside a method do not persist in mutsu) that is
unrelated to increment/decrement and is out of scope for this fix.

## The fix

`src/compiler/expr_postfix.rs` gained a shared helper,
`method_call_incdec_lvalue_target`, used by both the postfix (`compile_expr_postfix_inc`/`_dec`)
and prefix (`compile_prefix_incdec_method_lvalue`) compilation paths. It
extracts, from a `MethodCall`'s target expression, a pair of
`(expr-to-re-evaluate-the-invocant, name-string-for-optional-writeback)`:

- `Expr::Var`/`Expr::ArrayVar`/`Expr::HashVar` targets behave exactly as
  before (an `Expr::Var` under the sigil-prefixed name).
- `Expr::BareWord` targets (a package/type-object invocant, `Foo` in
  `Foo.counter++`) are now recognized too, re-evaluated as `Expr::BareWord`
  (not `Expr::Var`, which would incorrectly try an env lookup for a variable
  named `Foo`) so the accessor call runs against the actual `Package` value.

This routes `Foo.counter++`/`--`/`++Foo.counter` through the exact same
`__mutsu_assign_method_lvalue` → `assign_method_lvalue_with_values` →
class-level-attribute arm that `Foo.counter += 5` already used — no new
storage, no `++`-specific special case. The mechanism is general: it serves
`++`, `--`, and the prefix form uniformly (compound assignment already used
the equivalent `Expr::BareWord` handling in `compound_expr.rs`, unchanged by
this PR).

**The negative control is what makes this safe.** The class-level-attribute
arm in `assign_method_lvalue_with_values` is still tried *first*, and only
succeeds when `has_class_level_attr` recognizes the callee; an ordinary
`has $.x` (non-class-level, non-`rw`) accessor still falls through to the
existing "method is not rw" rejection further down the same function — a
`BareWord`/instance target with an ordinary non-rw accessor is not
newly writable. `B.new.x++` on `class B { has $.x = 0 }` still throws (as
`X::Assignment::RO` in mutsu; raku raises `X::Multi::NoMatch` for `++`
specifically, a pre-existing exception-class divergence from mutsu's `+=`
which already threw `X::Assignment::RO` for the same non-rw case before this
fix — unrelated to and unchanged by this PR).

## Verification

`t/class-level-attrs.t` grew from 32 to 43 assertions, covering: `Foo.counter++`/
`--`/prefix `++` on the type object, the `our` variant, `++` through an
instance, and the negative control (`has $.x` still rejects `++`/`+=`/`=`,
while `has $.x is rw` still allows `++`). All 43 pass under both `raku` and
mutsu. A targeted roast sweep (`S12-attributes/{mutators,instance,defaults}.t`,
`S03-operators/{autoincrement,increment,assign,autoincrement-range}.t`,
`S12-class/{attributes,rw}.t`, `S12-introspection/{attributes,can,methods,meta-class}.t`,
`S06-operator-overloading/sub.t`) shows no regressions. `make test` (3489
files, 34289 assertions) is green.
