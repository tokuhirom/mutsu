# A block reading its routine's `@_` no longer makes every store in the program write env

A read of an enclosing scope that the compiler has already resolved -- `OUTER::<$x>`, or a block in a method body reading the method's `@_` -- compiles to `GetOuterVar`. It was classified with `CALLER::` and symbolic dereference as a read of *another frame's* lexical, which sets a process-global latch: from then on every routine of the program mirrored its parameters and every local store into env. Concurrent::PriorityQueue's `method STORE(*@_) { $!lock.protect: { for @_ { ... } } }` set it, so every `($i = nqp::sub_i($i, 1))` step of Array::Sorted::Util's binary search paid an env write.

`GetOuterVar` names one of the scopes its code is written in, as an `EVAL` does, so it is now answered like one: the chunk that holds it, and every chunk declaring that chunk, keeps its lexicals visible by name (`static_name_lookup`), and nothing else changes.

The win is for the whole program, not one module: any program that loads a module whose code reads an enclosing scope stops mirroring every routine's parameters and every local store into env. On Concurrent::PriorityQueue's own loop the eliminated env writes are cheap (a handful of `insert_sym` per push, measured at ~0.1% of a push's instructions on a release build), so this is reported as strictly less work rather than a measurable speed-up. Found on the way: #17686 (`given ($x = ...)` binds a read-only topic). Refs #15786.
