# A re-used module lost its bare type alias, and a 2-char custom infix could shadow a longer built-in

Picked `IP::Addr` off the ecosystem lock board ([#7884](https://github.com/tokuhirom/mutsu/issues/7884)) and found two general interpreter bugs on the way from `blocked_load` to a running (if still partly red) suite.

**Module reuse lost the type alias for the second importer.** `IP::Addr::v4.rakumod` does `use IP::Addr::Handler; use IP::Addr::Common;`, and `IP::Addr::Handler` itself already `use`s `IP::Addr::Common`. By the time the direct `use IP::Addr::Common` ran, the module was already loaded, so it took the "already loaded" short-circuit path in `use_module_with_tags_inner` — which never re-established the bare short-name type alias for *this* importer's own scope. A nested `grammar IPv4-Grammar does IPv4-Basic { ... }` then failed to compose with `X::InvalidType: Invalid typename 'IPv4-Basic'`, even though the same bare name resolved fine as an ordinary term (`IPv4-Basic.^name`) moments earlier. `resolve_declared_type_name` (used by `is`/`does`/`hides` parent validation) checked only `env`, not the `package_type_alias` fallback that general type-name resolution (`has_type`) already consults for exactly this case. The bug needed the module's own declared `unit module` name to differ from how it is `use`d (as `IP::Addr::Common.rakumod` does, declaring `unit module IP::Addr::Const;`) to actually reproduce — a module whose file name and declared package agree didn't trigger it. Pinned by `t/modules/module-reused-role-does-in-nested-decl.t`.

**A 2-character custom infix operator could shadow a longer built-in one.** `IP::Addr` exports `multi infix:<==>(IP::Addr:D, IP::Addr:D)`. Once that was in scope, every later `===` in the importing file broke: `match_user_declared_infix_symbol_op` matched the declared `==` against the first two `=` of `===` and left a bare `=` behind, dying with "Confused. expected expression after infix operator". The existing single-character guards (pointy arrow, `++`/`--`, `+=`-style compound assignment) only covered 1-char symbols; the general "a custom operator ending in `=` must not claim a strict prefix of a longer `=`-chain" guard now applies at any length. Pinned by `t/oo/user-infix-symbol-does-not-shadow-longer-builtin.t`.

With both fixed, `IP::Addr`/`IP::Addr::v4`/`IP::Addr::v6` load cleanly (`load` all report `ok`; the ledger record moves `blocked_load` -> `red`, baseline assertions passing 0 -> 26/105). The remaining red funnels into two filed issues: [#8752](https://github.com/tokuhirom/mutsu/issues/8752) (`todo:deep`) — `.parse`/`.subparse` doesn't support a grammar's `method TOP` override, only `rule`/`token`/`regex TOP`, which blocks every file that calls `is-ipv4`/`.new`/`.set` — and [#8753](https://github.com/tokuhirom/mutsu/issues/8753) (`todo:ticket`) — an IPv6 grammar's embedded dotted-decimal IPv4 suffix (mapped/translated addresses) fails to match (4/30 assertions in `t/011-ipv6-grammar.rakutest`). `t/005-meta.rakutest`'s timeout is the already-tracked JSON::Fast ~300KB parse perf issue, [#8673](https://github.com/tokuhirom/mutsu/issues/8673).
